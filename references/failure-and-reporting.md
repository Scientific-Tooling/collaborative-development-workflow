# Failure Handling and User Reporting

Fallback and final-report rules. Read when a delegated task fails, is blocked, or the workflow is being handed off.

## Failure and fallback handling

- If subagent tools are unavailable, say so. The main agent may perform planning and implementation sequentially only when no child writer is live or claimed; if replacing a prior writer, follow the recovery path with confirmed stop/cancellation, a recovery `TaskSpec`, and an atomic lock transfer or distinct workspace. The main agent cannot substitute for the mandatory independent final reviewer; obtain another independent review mechanism or stop before acceptance and commit. Never claim that delegation or independent review occurred.
- Treat `NEEDS_INPUT` and `PARTIAL` as explicit coordination states, not automatic failures. For a live `NEEDS_INPUT` task, send the exact answer or decision to the same agent; if it is a material user choice, pause at the planning gate with a parent-created decision ticket whose applicable deadline and positive remaining budget must still pass a fresh monotonic check before continuation. An expired ticket, changed scope/plan, or unavailable invocation requires confirmed stop and a new bounded task or atomic lock transfer. For a terminal `PARTIAL` task, preserve its artifacts and content identity, then use the explicit same-task `PARTIAL → CLAIMED` CAS only when the parent-declared policy, runtime stop, checkpoint, and artifact proof establish resumability; carry the prior report/checkpoint context and unchanged fixed budget. For a reviewer, a replacement is allowed only for a proven non-resumable partial/failure. Never silently discard partial work or restart a live writer.
- Unless a task-specific override is explicitly set, enter one logical blocking wait by calling `wait_agent` with `timeout_ms` set to the remaining `attempt_deadline_at` (or the platform’s maximum accepted blocking timeout). The call may return sooner when the agent reaches a terminal state. If platform limits require continuation calls, the wait wrapper should automatically continue the same invocation; if the parent must continue it, those calls remain one logical wait and use the monotonic remaining budget. While it is waiting, do not issue status queries, inspect artifacts, read a moving diff, send liveness probes, retry, replace, take over, unlock a review, or mutate the child’s workspace. A passive progress timer must not wake the parent model or generate repeated progress messages.
- Use an explicit reviewer state machine: `RUNNING` → `WAITING` → (wait observation, remain `WAITING`) → `CANCEL_REQUESTED` → only an on-time runtime stop (`CANCELLED`/`FAILED` recovery predecessor), a late runtime stop (`BLOCKED` with `STOP_CONFIRMED_ONLY`), or an unverified stop (`REVIEW_BLOCKED` with the lock retained). `CLEAN` and `FINDINGS` are legal only from a validated live row with `overlay=NONE`; they are never successors of `CANCEL_REQUESTED`. `WAITING` means the parent is blocked on the same reviewer; an empty result, `timed_out: true`, wrapper yield, or `No agents completed yet` never authorizes a replacement or releases the review lock, and an early observation must continue the same bounded recovery wait. A confirmed runtime `shutdown` maps to non-resumable `CANCELLED`; an unconfirmed transport interruption is not terminal and retains its lock until reconciled. A `close_agent` response that reports `previous_status` is only pre-close evidence; it is not cancellation confirmation. A late runtime stop is committed as ledger `BLOCKED` with `terminal_reason=STOP_CONFIRMED_ONLY`, `overlay=CANCEL_REQUESTED`, and the retained lock; it is not a child terminal state and cannot authorize replacement. The reviewer task’s `CANCELLED`/`FAILED` state does not make the snapshot accepted: without a verified, runtime-bound `CLEAN` report and its parent/runtime coverage proof, the snapshot remains `REVIEW_BLOCKED`.
- Give each delegated planner and implementer one absolute wait budget (`planner_wait_budget` or `implementer_wait_budget`). Give the original reviewer the `review_initial_budget` slice and the snapshot-level `review_wait_budget`/`snapshot_deadline_at` the replacement may use. Reserve at least `review_replacement_decision_reserve_budget + review_spawn_reserve_budget + review_replacement_min_budget` before allowing a replacement; the total of all attempts, parent handoff, and binding overhead may never exceed the snapshot budget. If the orchestration wrapper yields a continuation or a platform timeout occurs before the current attempt is terminal, continue the same logical blocking wait with the remaining budget; do not turn it into a status-polling loop or restart the invocation.
- Only after the current attempt's absolute `attempt_deadline_at` is exhausted without a terminal response may the parent perform one bounded recovery status check. If the agent is still running, preserve its lock, request interruption or cancellation as appropriate, and wait until cancellation or another terminal state is confirmed before taking over or retrying; do not wait past the fixed `recovery_deadline` or spend the replacement reserve on the cancellation handshake.
- Validate runtime-owned terminal timing before any state transition: all samples must use the same monotonic clock; `spawn_requested_at <= spawn_confirmed_at <= monotonic_now`, and a real `started_at` must lie in that interval. A normally bound result must also satisfy `spawn_confirmed_at <= terminal_at <= monotonic_now` and `started_at <= terminal_at` when `started_at` exists. A prebinding terminal candidate may use its runtime-captured `prebinding_terminal_at` only when `spawn_requested_at <= prebinding_terminal_at <= monotonic_now` and the bound `terminal_at` is exactly that sample. An original role-complete result must have `terminal_at <= attempt_deadline_at`, a replacement role-complete result must have `terminal_at <= snapshot_deadline_at`, and an on-time stop/cancellation event must have `terminal_at <= recovery_deadline` (or the binding-failure deadline). Only a runtime-owned `STOP_CONFIRMED` after the applicable fixed stop deadline may exceed it, and that event is `STOP_CONFIRMED_ONLY`, never review or recovery authority. Missing, reversed, early, future, or late child timestamps are quarantined; recovery time never becomes review time.
- Replace a reviewer only after its terminal state or confirmed cancellation, and no more than `review_replacement_limit` time per snapshot. The parent must complete its recovery/CAS handoff by `snapshot_deadline_at - review_spawn_reserve_budget - review_replacement_min_budget`; the replacement request then requires at least `review_spawn_reserve_budget + review_replacement_min_budget` of unused snapshot budget and receives no more than `remaining(snapshot_deadline_at)`. Atomically claim the single replacement slot and review ownership immediately before the spawn; recheck finite, nonnegative monotonic remaining values and the replacement gate immediately before the spawn, at the runtime-atomic spawn boundary, at binding, and again when a prebinding terminal payload is late-bound. The late-bind report CAS must carry the exact validated budget-gate fields, and a missing, reversed, overrun, or below-minimum gate quarantines the payload without creating a report. Its TaskSpec must record `REPLACEMENT_OF`, the original terminal/cancellation event, the same immutable snapshot identity, `budget_remaining_at_spawn`, `budget_remaining_at_binding`, and the fixed `snapshot_deadline_at`; it must never receive a fresh budget merely because its scope is narrower. Do not spawn a replacement while the original may still be running. Use `send_input` for a live `NEEDS_INPUT` task. Use `resume_agent` only for an explicitly resumable `PARTIAL`, or for a platform-confirmed resumable `interrupted` result after normalizing it to ledger `PARTIAL`; a confirmed `shutdown`, `completed`, `errored`, `FAILED`, `CANCELLED`, or `REVIEW_BLOCKED` agent is terminal and must not be resumed.
- A late runtime `STOP_CONFIRMED` is committed as ledger `BLOCKED` with `terminal_reason=STOP_CONFIRMED_ONLY`, `overlay=CANCEL_REQUESTED`, and the retained owner/lock; the disposition is not a report status and cannot resume, replace, unlock, or satisfy review. Every child report received after `CANCEL_REQUESTED`, including failure/cancellation/shutdown reports, is fully scanned and quarantined; only a dedicated on-time runtime interruption or started runtime-terminal event can enter recovery. A reviewer `PARTIAL` with a valid runtime/parent checkpoint must call the explicit same-task resumable `PARTIAL → CLAIMED` CAS, carry prior context, and preserve the fixed budget; `recover_or_block()` and reviewer replacement are reserved for non-resumable recovery.
- Do not probe liveness during an active wait. After the absolute budget, absence of a changed file or intermediate output is still not evidence of failure; use the single bounded recovery check above. If a planner remains unavailable after confirmed terminal/cancellation, the main agent finalizes the plan. If an integrated reviewer remains unavailable after confirmed terminal/cancellation, use the one permitted replacement reviewer. A fixed parallel review set is selected at the initial snapshot freeze only when the scope was already judged broad; a no-report observation does not switch an integrated review into a set within the same snapshot. The main agent’s self-review never substitutes for the mandatory independent final review; an unavailable lane leaves the aggregate `REVIEW_BLOCKED`.
- Except for the explicit `SPAWN_UNCONFIRMED` post-spawn binding-failure exception above, only after the current attempt deadline is exhausted and the single bounded recovery check fails to establish a terminal state may the parent request an interrupting checkpoint, cancellation, or stop. Do not issue that ordinary recovery request earlier. Preserve every usable output and observed artifact. Confirm that a writer stopped before allowing another writer into that mutable workspace. Once confirmed and safe, resume the same task only when a compare-and-set check proves an explicitly resumable `PARTIAL` state; a platform-confirmed resumable `interrupted` result must first be recorded as `PARTIAL` with its interruption event, preserved artifact identity, retained lock, and `RESUMABLE: yes`, then reclaimed through `PARTIAL → CLAIMED` with the same `task_id`, scope, incremented `attempt`, and new `invocation_id`. The resumed invocation must receive the prior validated report and a concise continuation summary in its context manifest. A confirmed `shutdown` is mapped to `CANCELLED`, never resumed. Otherwise create a new bounded recovery `TaskSpec` with a new task ID and invocation, and give it the same prior report and continuation summary plus the last accepted checkpoint or other known content-identified snapshot. For a reviewer replacement, the new TaskSpec must additionally carry `REPLACEMENT_OF`, the original `snapshot_deadline_at`, and the remaining-budget calculation; it may consume only the remaining snapshot budget and may not reset or extend it. If the parent-side decision deadline has passed, or `remaining(snapshot_deadline_at) < review_spawn_reserve_budget + review_replacement_min_budget`, do not spawn the replacement. If binding overruns the reserve or the permitted replacement yields no usable terminal report, mark the snapshot `REVIEW_BLOCKED` and stop before acceptance/commit. In either case, preserve the old attempt and require report verification, integration checks, and normal `ACCEPTED` gating before any dependent work proceeds.
- If stop cannot be confirmed, never create a replacement reviewer: retain the review lock, keep the attempt `SPAWN_UNCONFIRMED`/`CANCEL_REQUESTED`, quarantine late reviewer output, and mark the snapshot `REVIEW_BLOCKED` when the bounded recovery deadline or snapshot budget is exhausted. For a writer-only recovery exception, create a new bounded recovery `TaskSpec` in an isolated workspace from the last accepted checkpoint or another known content-identified snapshot, with a distinct lock and invocation identity. Do not call that workspace authoritative merely because the original is unavailable: it is only a candidate integration source until its own report is verified, its focused checks pass, and the main agent completes the normal integration and `ACCEPTED` transitions. Keep the original task/attempt owned or quarantined, quarantine late original-writer output from automatic integration, and never reassign its mutable workspace. After the original writer state is known, allow one new recovery writer—or a main-agent takeover represented by the same new recovery task—to inspect and reconcile only useful, non-conflicting artifacts. Never blind-merge, share a mutable workspace, or discard useful partial work merely to restart.
- If an entire review set is blocked by unavailable/no-report reviewer invocations, an explicitly authorized fresh review round may use an independent runtime/provider/model as described in section 4. It must receive a new immutable snapshot and new run/set identities, use a separately reserved budget, and produce a complete validated review result; old set attempts remain blocked audit records and never contribute coverage. A different model or channel is useful only when it is a genuinely fresh invocation with no inherited context, not when it merely resumes or paraphrases the unavailable reviewer.
- If a tool returns a fork or patch that is not present in the review worktree, integrate or inspect the actual artifact before proceeding.
- If tests require network access, credentials, production access, or a destructive operation, stop at that boundary and request approval or a safe alternative.
- Close completed subagents when they are no longer needed so they do not consume concurrency capacity.

## Final user report

Report the outcome first, then include:

- the implemented behavior and important files;
- review rounds and whether any actionable findings remained;
- independent-review recovery details when applicable: snapshot identity, original/replacement terminal state, consumed and remaining budget, cancellation confirmation, and whether acceptance was `REVIEW_BLOCKED`;
- validation commands and results;
- commit hash and message, if committed;
- any pre-existing changes intentionally left untouched;
- remaining caveats or follow-up actions.
